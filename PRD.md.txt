## Overview

`cxas-scrapi` (CX Agent Studio Scripting API) is Google Cloud Platform's open-source Python SDK, CLI, and Agent Skills toolkit for building, evaluating, and deploying Conversational Agents (CES/Dialogflow CX successor) . It is structured around a `core` module (Apps, Agents, Tools, Guardrails, Deployments, Sessions resources), a `utils` module (pagination, proto conversion, Sheets/BigQuery integrations), an `evals` module (golden tests, simulations, latency metrics), a `cli` module (the `cxas` command, including `cxas lint` and `cxas llm-lint`), and a `migration` module for legacy Dialogflow CX → CXAS conversion . It targets Python 3.10+ and depends on a large surface of libraries including `google-cloud-ces`, `google-genai`, `pandas`, `gspread`, `pydub`, `InquirerPy`, and `scikit-learn` . This report catalogs the project's documented limitations from its own issue tracker and codebase structure, then lays out a full plan to build a Rust reimplementation — referred to here as `cxas-harness` — using the "Gauntlet Loop" AI-agent development methodology.

## Limitations of the Existing Python Harness

The repository's open issues reveal concrete, recurring pain points rather than speculative ones. Grouping the 25 open issues by theme surfaces four categories of weakness: correctness bugs in evaluation/simulation, scalability/regional constraints, CLI/DX friction, and architectural rigidity .

### Correctness and reliability bugs

| Issue | Problem | Root cause category |
|---|---|---|
| #355 | Simulation evals repeat the first `static_utterance` instead of advancing | State-machine bug in eval loop |
| #345 | DTMF simulations hang because `BidiSessionHandler` never waits for the agent's turn | Async/bidi-streaming concurrency bug |
| #284 | `wait_for_run_and_get_results` crashes with `'int' object has no attribute 'name'` when server returns an `EvaluationRunState` the installed protobuf stubs don't define | Weak typing / stub drift between generated protobufs and server enums |
| #298 | Apps 4MB or larger cannot be pulled | Payload/streaming size limits not handled |
| #394 | Tool deletion in Cloud isn't 100% reflected locally | Local/remote state sync gap |
| #136 | Voice channel simulations don't evaluate the returned audio | Incomplete multimodal eval coverage |
| #168 | Automated hillclimbing leaves behind entire agent snapshots | Resource cleanup / lifecycle bug |
| #86 | Missing root-agent validation in `cxas lint` causes failed pushes | Incomplete static validation coverage |

The `'int' object has no attribute 'name'` bug (#284) is emblematic of a class of failures common in dynamically typed Python SDKs that wrap gRPC/protobuf services: enum values returned by the server can silently diverge from what's baked into the installed client stubs, and Python's duck typing lets this pass until runtime. A statically typed language with exhaustive `match` semantics over enums would surface this at compile time instead of in production evaluation runs.

### Regulatory, quota, and scaling constraints

Issue #401 is explicitly labeled a "Blocker": vertex_location is hardcoded to `"global"` inside the evaluations module, which prevents any usage in regulated industries requiring regional data residency. Issue #263 asks for evals to use a dedicated `Evaluation RunSession` quota instead of piggybacking on the general `RunSession` quota, implying the current design causes quota contention between normal agent operation and evaluation workloads. Issue #270 ("Unified Workspace Resolution & Cascading Profiles") and #131 (an RFC for `cxas diff`/`cxas state` drift-attribution primitives) both point to the lack of a coherent state/config model — teams working across GUI and IDE currently have no reliable way to detect or resolve configuration drift.

### CLI ergonomics and automation friction

Issue #55, "Improve cxas CLI ergonomics for coding agents and automation," is a direct signal that the current CLI's output formats and invocation patterns are not well suited to being driven by other automated agents or CI pipelines. Related issues #54 (multi-environment GitHub Actions generation) and #46 (formal GitHub Actions) show that first-class CI/CD integration is still missing, meaning teams must hand-roll automation around the CLI. Issue #350 requests that `cxas trace` include per-turn raw JSON, indicating current tracing output is too lossy for deep debugging.

### Architectural and dependency weight

The dependency list in `pyproject.toml` spans over 30 packages, including heavyweight, loosely related libraries such as `scikit-learn`, `pandas-gbq`, `google-cloud-bigquery`, `gspread`, `pydub`, and `graphviz` bundled into a single monolithic package rather than split into optional extras beyond `dev`/`docs`. This means a minimal CLI/lint use case still pulls in machine learning and audio-processing dependencies, inflating install size, cold-start time, and attack surface — a common Python packaging anti-pattern that a modular Rust crate workspace naturally avoids. The `migration` module's `InquirerPy`-based interactive TUI is documented as "imported lazily" specifically to avoid this cost for callers who don't need it, which is itself an admission of the packaging problem. Additionally, distributing "Agent Skills" as raw filesystem directories (`.agents`, `.claude`, `.gemini`) copied via `hatch.build.targets.wheel.shared-data` is fragile versioning-wise compared to a compiled, versioned binary artifact.

### Summary of limitation classes

| Category | Representative issues | Underlying weakness |
|---|---|---|
| Correctness/concurrency bugs | #355, #345, #284, #394, #136 | Dynamic typing, weak state machines, incomplete async handling |
| Regional/regulatory blockers | #401, #263 | Hardcoded config, single quota pool |
| Config/state coherence | #270, #131 | No unified, verifiable state model |
| CLI/automation ergonomics | #55, #54, #46, #350 | Human-first CLI design, no machine-readable contract |
| Packaging/performance | pyproject.toml dependency graph | Monolithic Python package, no compile-time guarantees |

## Design Goals for cxas-harness (Rust)

Given these limitations, the Rust rewrite should optimize for: compile-time correctness over protobuf/enum drift, first-class async/bidi-streaming safety, regional configurability as a core primitive (not a hardcoded default), a machine-first CLI (structured JSON output, stable exit codes, non-interactive mode by default), and a modular crate workspace so consumers only pull in what they need (e.g., `cxas-core`, `cxas-evals`, `cxas-cli`, `cxas-migration` as separate crates).

## Full Development Plan

### Phase 0 — Foundations and parity contract

Before writing Rust, establish a "parity contract": enumerate every public class/method in `cxas_scrapi.core`, `evals`, `cli`, and `migration`, and every documented CLI subcommand, turning the existing Python surface into a machine-readable spec (e.g., a YAML/JSON API manifest). This spec becomes the acceptance criteria for the Gauntlet Loop's critics later. Also vendor the CES/Dialogflow CX protobuf definitions and generate Rust bindings (via `tonic`/`prost`) so the enum-drift bug class (#284) is closed by construction — the compiler rejects unmatched enum variants.

### Phase 1 — Crate architecture

Structure the workspace to mirror and improve on the Python library composition described in the README :

- `cxas-proto`: generated gRPC/protobuf bindings for CES, kept in lockstep with the SDK version via CI checks (directly targets the stub-drift bug, #284).
- `cxas-core`: Apps, Agents, Tools, Guardrails, Deployments, Sessions — pure async Rust (`tokio` + `tonic`), with `location` as a mandatory typed field (never a hardcoded default), directly resolving #401.
- `cxas-utils`: pagination, response flattening, Sheets/BigQuery adapters — feature-flagged so they're compiled only when requested, addressing the packaging bloat problem.
- `cxas-evals`: golden tests, simulation runs, latency metrics, with an explicit typed state machine for simulation turn progression (fixes the "repeats first static_utterance" bug, #355) and a dedicated quota-aware client for evaluation `RunSession`s (#263).
- `cxas-migration`: Dialogflow CX → CXAS conversion tooling, with a non-interactive mode by default and an optional TUI behind a feature flag (mirrors the lazy-`InquirerPy` pattern but makes it structural rather than an afterthought).
- `cxas-cli`: the `cxas` binary, emitting structured JSON alongside human-readable output, explicitly designed for coding-agent consumption (directly answers #55), plus native GitHub Actions templates generated as a first-class subcommand (#54, #46).
- `cxas-state`: a new crate with no Python equivalent — implements content-addressed hashing of agent configuration for `cxas diff`/`cxas state` drift detection, resolving #131 and #270.

### Phase 2 — Bidi-streaming and concurrency correctness

Rebuild the DTMF/voice session handler using `tokio::select!` with explicit turn-state enums (`AwaitingUserTurn`, `AwaitingAgentTurn`, `Terminated`) instead of implicit flags, closing #345. Extend the audio evaluation path to score returned TTS/audio output against expected transcripts using a pluggable scorer trait, closing #136 and unblocking issue #27 (Audio Evaluations).

### Phase 3 — Lint and validation engine

Port `cxas lint`'s 60+ structural/schema checks as a rule-registry pattern in Rust where each rule is a `trait LintRule` implementation with unit tests, ensuring the missing root-agent validation gap (#86) and any future gaps are caught by a completeness test that diffs the rule registry against the schema's required fields. Port `cxas llm-lint` as a thin client calling Gemini via `google-genai`-equivalent Rust HTTP client, preserving the AI-driven semantic review capability.

### Phase 4 — Migration and eval-run cleanup

Implement resource-lifecycle guards (RAII-style `Drop` handlers) around agent snapshots created during automated hillclimbing so that even on panic or task cancellation, orphaned snapshots are cleaned up — directly resolving #168. Ensure tool-deletion sync between local and cloud state is verified via the new `cxas-state` hashing layer, resolving #394.

### Phase 5 — Packaging, docs, and release

Publish `cxas-harness` as a single statically linked binary (via `cargo dist` or `cross`) per platform, eliminating Python's `uv sync`/virtualenv setup step entirely. Port the MkDocs Material documentation site content to the same generator (or migrate to `mdBook`), preserving the Docs/Examples/Agent Skills/Core SDK link structure from the original README . Add native GitHub Actions workflow generation as a `cxas actions init` subcommand.

## Applying the Gauntlet Loop

The Gauntlet Loop is an AI-agent-driven iterative build methodology in which a lead/orchestrator agent decomposes a goal into independently buildable pieces, assigns each piece to a builder sub-agent, and pairs every builder with a separate, context-blind critic sub-agent that judges the output against a concrete quality benchmark; failed pieces are sent back for another build-critique cycle, and the loop has no fixed end — only a quality bar and budget/iteration caps as stop conditions. Three structural upgrades distinguish it from a simple single-builder/single-critic loop: the work is fanned out to many specialist sub-agents in parallel, every sub-agent has its own dedicated critic (not one shared critic for the whole project), and the critic is "blind" — it only inspects finished evidence (test output, screenshots, benchmark comparisons), never the builder's code or reasoning, which prevents the critic from being swayed by the builder's explanations.[1][2][3][4][5]

### Step 1 — Set the goal, not the implementation

Per Gauntlet Loop practice, give the orchestrator agent the target outcome (rewrite `cxas-scrapi` as a correctness- and ergonomics-improved Rust harness, `cxas-harness`) without prescribing exact code structure, so it has room to find the best Rust-idiomatic approach. The parity-contract manifest from Phase 0 plus the limitation table above becomes the "task" input.[6]

### Step 2 — Establish the real-world quality benchmark

Gauntlet Loop emphasizes that critics are only as sharp as what they compare against. For `cxas-harness`, the benchmark is concrete and dual-sided: (a) full behavioral parity against the existing Python `cxas-scrapi` test suite and documented CLI outputs, and (b) a "bug closure" checklist derived directly from the 25 open GitHub issues cataloged above — each closed issue is a pass/fail gate, not a subjective judgment . This mirrors the pattern of using a concrete reference (a real game, a real screenshot) rather than a vague "make it good" instruction.[2][3]

### Step 3 — Fan out builder sub-agents by crate

Split the work along the Phase 1 crate boundaries: one builder sub-agent per crate (`cxas-proto`, `cxas-core`, `cxas-utils`, `cxas-evals`, `cxas-migration`, `cxas-cli`, `cxas-state`). This matches the Gauntlet Loop pattern of assigning each component (lighting, physics, sound, etc., in the game-building examples) to its own specialist builder working in parallel rather than one agent juggling the entire codebase. Following the git-worktree discipline described in Gauntlet Loop write-ups, each builder works in an isolated git worktree/feature branch and commits before requesting critique, so failures are isolated and the orchestrator can merge only what passes.[3][4][1]

### Step 4 — Pair each builder with a blind critic

Every builder crate gets a dedicated critic sub-agent that never sees the builder's source code or rationale — only the evidence: `cargo test` output, `cargo clippy` lint results, a diff against the parity manifest, and reproduction of the specific GitHub issue's bug scenario (e.g., for the critic reviewing `cxas-evals`, the evidence is "does simulation now advance past the first static_utterance," directly testing #355). The critic scores the submission, identifies the single biggest remaining gap, and returns that feedback as the next prompt to the builder — it never lowers the bar or narrows scope, consistent with Gauntlet Loop's rule that critics must not act as implementers and must not relax requirements.[1][2][3]

### Step 5 — Loop until the gauntlet is survived

Each builder/critic pair iterates — build, run tests, get scored, receive the top-priority fix, rebuild — until that piece's critic is satisfied that the crate provides full functionality, has test coverage for every flow including edge cases (explicitly, unit tests reproducing each of the 8 correctness bugs listed above), contains no dead code or duplicate logic, and introduces no new regressions or security issues. Because a gauntlet has no single judge but "a whole line of them," the crate isn't declared done until it survives all of these individually — the parity check, the clippy/lint pass, the reproduction test for its assigned GitHub issue(s), and a performance/binary-size check against the Phase 5 packaging goals.[3][1]

### Step 6 — Orchestrator-only merge authority

The lead/orchestrator agent's role is purely to plan, fan out, and merge — it never implements and never critiques, preserving the strict separation of roles that Gauntlet Loop write-ups identify as essential to avoiding self-graded work. Only after a crate's critic declares success does the orchestrator merge that feature branch into the main integration branch; cross-crate integration (e.g., `cxas-cli` calling into `cxas-core` and `cxas-evals`) becomes its own subsequent gauntlet round with its own critic focused purely on end-to-end CLI behavior against the original Python CLI's documented commands.[2][1]

### Step 7 — No fixed finish line, explicit stop conditions

Consistent with the "loop has no finish line, only a real benchmark" principle, the practical stop conditions for this project should still be made explicit to avoid runaway iteration: a per-crate iteration cap, a total compute/time budget for the whole rewrite, and a final "release candidate" gate requiring 100% of the 25 cataloged issues to have a corresponding closing test, before the orchestrator hands the result back for human review.[4][3]

This plan treats the Python project's own issue tracker as the ground truth for what "better" means, then uses the Gauntlet Loop's builder/blind-critic/no-self-grading structure to drive the Rust rewrite toward objectively verifiable parity and bug closure rather than subjective code review

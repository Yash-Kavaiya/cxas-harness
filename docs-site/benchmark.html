Benchmark and Gauntlet Loop

A critic is only as sharp as the reference it compares against. This page describes the reference, and the loop built on top of it.

The defect that motivated this

crates/cxas-proto declared the CES evaluation run state as:

Unspecified, Pending, Running, Succeeded, Failed, Cancelled

CES declares it as:

EVALUATION_RUN_STATE_UNSPECIFIED, QUEUED, RUNNING, COMPLETED, ERROR, CANCELLED

Three of six variants were invented, and as_str_name() emitted "PENDING", "SUCCEEDED" and "FAILED" — strings the CES API has never used. The test that supposedly closed the enum-drift bug (#284) had itself drifted, and 78 passing tests could not see it.

The old parity contract could not have caught it. It asserted that a checked-in YAML file contained strings that the same YAML file declared, so it could never fail.

The reference

The benchmark is now Google's own machine-readable discovery documents, vendored under reference/ces/:

v1v1betatotal
REST methods66104170
Schemas219333552
Schema enum fields4886134
Parameter enums5510

Both are pinned at revision 20260806 and verified by sha256 against PINNED.toml, so a truncated or hand-edited reference is rejected rather than silently measured.

Every evaluation resource — evaluations, evaluationRuns, evaluationDatasets, evaluationExpectations, scheduledEvaluationRuns — exists only on v1beta. A test enforces that nothing models evaluations against v1, where they do not exist at all.

Replica skew

The discovery endpoint is served from replicas that disagree. Fetching ?version=v1 repeatedly returns revision 20260730 and 20260806 in no stable order, so a byte-comparison drift check flapped between pass and fail against an unchanged upstream. The refresh tool fetches five times, keeps the highest revision, and treats the pinned revision as a high-water mark: drift is reported only when upstream publishes something newer, or when bytes change at the same revision.

What is enforced

TestAsserts
enum_variants_match_discoveryevery declared enum variant matches its CES wire spelling exactly
declared_methods_resolve_in_discoveryevery method cxas-core declares exists in discovery with the same verb and path template
declared_table_matches_discovery_exactlythe generated table and the reference agree in both directions -- a method CES added that the table lacks fails too
modelled_methods_are_addressablenothing in MODELLED names a method CES no longer declares
evaluation_methods_are_never_declared_against_v1no evaluation method is registered on a surface that has none
coverage_reportreports implemented/total; deliberately does not gate

The coverage report does not gate on purpose. A pass/fail threshold can be satisfied by deleting the metric; a printed number cannot.

CES-COVERAGE addressable v1=66/66 v1beta=104/104 total=170/170 modelled=37/170

Two numbers because they mean different things. Addressable is generated from the discovery documents and says a request can be built and sent. Modelled is hand-written and says this workspace has an opinion about what the resource is and what failure means for it. Reporting only the first would be the same flattery this page exists to argue against.

Generated, not hand-listed

The method table is produced by tools/generate_methods.py and checked in, rather than built by a build.rs. A build script that parsed JSON would make every downstream build depend on the reference files; one that fetched them would make builds depend on the network. Checking the table in keeps the build hermetic.

Because the table is generated from the reference, the parity test comparing them is a staleness check rather than an independent verification -- and staleness is the failure that actually happens. Refreshing the reference without regenerating leaves the table describing an API that is no longer the pinned one, and nothing else in the workspace would notice.

python tools/generate_methods.py           # regenerate
python tools/generate_methods.py --check   # fail if stale

The Gauntlet Loop

gauntlet/ is repo tooling and is never shipped in the cxas binary — nothing under it is a Cargo workspace member. Three roles, separated structurally rather than by instruction:

RoleSeesMay
Orchestratorscorecardsplan, fan out, merge — never implement or critique
Builderits own crate, the critic's last gapedit that crate only
Criticthe evidence bundle, nothing elsescore and name one gap — never implement

The evidence bundle is built by gauntlet/evidence.py — deterministic code, not an agent — after the builder finishes, so the builder cannot shape what the critic sees.

Critic receivesCritic never receives
cargo test outputcrate source code
cargo clippy outputthe diff
discovery coverage and revisionscommit messages
assigned-issue reproductionsthe builder's rationale
binary sizeany self-assessment

That blindness is asserted, not merely documented: test_bundle_excludes_source_code fails if source ever reaches a critic. If it did, the loop would degenerate into self-grading — the exact failure this design exists to prevent.

Running it

python gauntlet/orchestrator.py             # every piece
python gauntlet/orchestrator.py cxas-proto  # one piece

agent_cmd in gauntlet/config.toml is any CLI that reads a prompt on stdin and writes a response on stdout — claude -p, gemini -p, codex exec. No provider SDK is imported, so swapping providers is a one-line change.

Stop conditions

The loop has no natural finish line, so the stop conditions are explicit: max_rounds per piece, budget_usd overall, and a release-candidate gate requiring every catalogued issue to have a reproduction test, full enum parity against discovery, and coverage at or above rc_coverage_min. On reaching the gate the orchestrator stops and hands back for human review.

A round fails — never silently passes — when the critic returns unparseable output, returns nothing, or when the configured agent binary is missing or times out. Silence is not consent.

Refreshing the reference

python tools/refresh_reference.py           # re-vendor and re-pin
python tools/refresh_reference.py --check   # fail if upstream is newer

The --check form runs in CI so upstream API drift arrives as a reviewable pull request rather than a silent behavioural change.

Bottom line. cxas-harness is a faithful, more disciplined re-implementation of cxas-scrapi's CLI surface — same command verbs, deterministic machine-first output, and a real (verified) REST transport — with the Gauntlet Loop as its quality engine. The loop's core design is sound and test-enforced; the gaps are in enforcement breadth (worktree isolation, issue-repro evidence, edit scope), listed in section 5.

Findings from the sweep.
  1. apps get / delete id-matching gap — lookups compare against the full resource name or the display name, never the trailing id segment. apps get --app support-agent returns CES_NOT_FOUND for an app that exists, and delete --app support-agent returns ok with "deleted": false. Matching the final path segment (or the --app-id used at create time) would fix both.
  2. Live transport confirmed working — the 403 came back from Google's API gate, not from the client. That is exactly the honesty claim in the README: everything up to "project has the API enabled" is real; nothing in the test suite has ever faked it.
  3. Exit-code discipline holds — 0 ok / 1 runtime (CES, DRIFT, CES_NOT_FOUND) / 2 usage (MISSING_PARAMETER, USAGE, TTY_REQUIRED, FEATURE_DISABLED).
  4. Everything is JSON — even clap usage errors and credential failures come back as the same envelope. Scriptable without a parser beyond jq.
  5. Gated verbs are honest — run-session and llm-lint fail loudly with distinct codes rather than pretending to work.

4 · Creating agents with cxas-harness

Two paths exist: a local scaffold you author and lint (offline, works today), and a live CES-side create via the generic API surface (needs a real project with the CES API enabled — verified 403 on project demo).

4.1 Local agent scaffold

cxas init --app-dir ./my-app        # app.yaml + agents/main/instruction.txt
mkdir -p my-app/agents/billing
echo "you are the billing agent, handle invoices" > my-app/agents/billing/instruction.txt
mkdir -p my-app/agents/support/tools
cat > my-app/agents/support/tools/order.yaml <<'EOF'
name: check_order_status
description: look up order status
EOF
echo "you are the support agent, resolve tickets" > my-app/agents/support/instruction.txt
cxas lint --app-dir my-app           # 0 errors; V0xx info diagnostics for optional files
cxas agent --app-dir my-app          # {"ok":true,"error_count":0}

The resulting tree (verified):

my-app/
  app.yaml
  agents/
    main/instruction.txt
    billing/instruction.txt
    support/instruction.txt
    support/tools/order.yaml
  .github/workflows/test_local.yml      # from `cxas actions init`
  .github/workflows/cleanup_local.yml

4.2 Registering apps in the catalog

cxas create --name "Support Agent" --app-id support-agent \
  --project-id demo --location us-central1        # {"name":"projects/demo/locations/us-central1/apps/support-agent"}
cxas apps list --location us-central1 --project-id demo
cxas branch --source support-agent --new-name support-agent-v2 \
  --project-id demo --location us-central1
cxas push --app-dir my-app --app "Support Agent" \
  --project-id demo --location us-central1

All of these persist to the catalog (.cxas/catalog.json or $CXAS_CATALOG) — a deterministic, inspectable local model of apps, deployments, conversations, versions and evaluations.

4.3 Live agent creation against CES

cxas api describe ces.projects.locations.apps.agents.create --api-version v1beta
# POST v1beta/{+parent}/agents, parameter: parent

# Once a project has the CES API enabled + ADC authenticated:
cxas api call ces.projects.locations.apps.agents.create \
  --param parent=projects/REAL-PROJECT/locations/us-central1/apps/REAL-APP \
  --body '{"display_name":"My Agent","instruction":"you are…"}'

Run with the demo project this resolved credentials but returned Google's 403 SERVICE_DISABLED — the correct first step is enabling ces.googleapis.com on the project, then the same command works.

5 · Is the Gauntlet Loop a proper implementation?

Verdict: yes — the core is properly implemented, and unusually honestly. The parts that are easy to fake (blindness, stop conditions) are enforced in code and covered by tests, all 32 of which pass. The loop was verified by reading orchestrator.py, evidence.py, the role prompts, and running its suite.

5.1 What is genuinely right (and verified)

PropertyHow it is enforced, not just claimed
Blind criticFORBIDDEN_KEYS in evidence.py + test_bundle_excludes_source_code / test_rendered_bundle_contains_no_rust_source — source reaching a critic fails the suite
Builder cannot shape evidenceBundle is built by deterministic code after the builder subprocess returns; the builder's stdout is discarded
Real stop conditionsmax_rounds, max_agent_calls, rc_coverage_min are read and enforced; a round that cannot afford both calls is not started; test_stop_conditions.py fails if budget_usd ever returns
Fail is failUnparseable critic output, empty output, missing agent binary, or timeout all resolve to a FAILED round — silence is not consent
Provider-agnosticNo SDK imported; agent_cmd is any stdin/stdout CLI
Reference that can failThe benchmark is Google's own discovery documents (sha256-pinned); it already caught the EvaluationRunState enum drift that 78 green tests missed — the parity contract now checks both directions
Honest coverage reportingCES-COVERAGE addressable v1=66/66 v1beta=104/104 total=170/170 modelled=37/170 — verified live; a reported number instead of a gated threshold

5.2 Gaps and improvements (ranked by value)

  1. Issue-repro evidence is missing from the bundle. The design doc and the critic prompt both say "assigned issues — is there evidence each is genuinely closed", but evidence.py only ships test/clippy output, upstream coverage counts, and binary size. It never runs an issue reproduction. The entire reason the loop exists is a test that passed while asserting the wrong enum — so the loop currently re-runs the same class of failure: a critic told "issue #284 is assigned" with no repro evidence can only take the builder's word through test names. Fix: add a per-issue repro step to build_bundle (e.g. run the specific closing test with --exact, or a tiny per-issue script) and include pass/fail per issue number.
  2. Worktree isolation is promised but not enforced. The spec says the builder works "in its own git worktree, committing before requesting critique"; the README warns "the builder edits your working tree". The orchestrator runs the builder directly against the repo. Fix: have the orchestrator create a throwaway worktree per piece (or snapshot git stash/commit), so a bad builder can never corrupt the user's tree, and verify a commit exists before critiquing.
  3. Builder edit scope is unchecked. builder.md forbids touching gauntlet/ or other crates, but nothing detects it. Fix: in evidence.py, run git diff --name-only filtered to the piece's path — assert scope without leaking diff content (the blindness tests already keep content out; scope metadata is safe). An out-of-scope edit = automatic FAIL.
  4. Builder subprocess results are discarded. invoke_agent returns stdout that the builder call ignores; a builder that crashed (non-zero exit) still gets critiqued — a wasted round, and a crash with a partially-applied edit gets graded as if deliberate. Fix: check the builder's returncode; a crash is a FAILED round, matching the critic-side discipline.
  5. Evidence shows upstream coverage, not per-piece progress. The critic sees "v1: 66 methods" — the same number every round regardless of what the builder did. Fix: include the CES-COVERAGE line from cargo test -p cxas-parity and the modelled count, so a critic can see whether a piece actually moved the number.
  6. Binary size has no baseline. The critic is told to judge binary size "against the packaging goal of a lean static binary" but receives a raw byte count with no threshold or trend. Fix: record previous-round size and a target; or drop it from the bundle until there is one.
  7. Score rubric has no anchors. A 0–100 score with no calibration can pass at 50 one round and fail at 80 the next. Fix: give the critic prompt anchor definitions (e.g. 90+ = all issues evidenced + zero clippy, 70–89 = …) so scores are comparable across rounds and pieces.
  8. Pieces run sequentially. Nine crates × up to 8 rounds is fine to serialize, but the budget is shared and idle time adds up. Fix: fan out pieces to concurrent workers against a shared CallBudget (a lock or a counter thread) — the budget math is already central.
  9. Per-call timeout is fixed at 1800s. A hung agent burns half an hour and a budget slot. Fix: make the timeout configurable and shorter per role (builder typically needs more than critic).
  10. rc_coverage_min = 0 makes the RC gate vacuous today. A clean sweep below the bar correctly exits non-zero — but with the default 0, any sweep is a "release candidate". Fix: set a real number (the design doc suggests the phase-3 gated subset) or fail loudly when the gate is 0.
Honest framing. Items 1–3 are the ones that matter: they are exactly the kind of enforcement the loop already does well for blindness and budgets, applied to the remaining "claimed but not enforced" surfaces. The rest are ergonomics. The design's own amendment history (budget_usd → max_agent_calls) shows the project already treats "documented but unenforced" as the enemy — these are the next instances of it.

6 · Quickstart

cargo build -p cxas-cli                       # build
./target/debug/cxas --help                    # 36 commands
cxas init --app-dir ./my-app                  # scaffold an agent app
cxas lint --app-dir ./my-app                  # deterministic lint
cxas api list --filter evaluationRuns         # offline method table
cxas api call ces.projects.locations.apps.list \
  --param parent=projects/$PROJECT/locations/$LOC  # live, needs ADC + enabled API

python -m pytest gauntlet/tests -q            # 32 tests, verifies the loop itself
python gauntlet/orchestrator.py cxas-proto    # one-piece Gauntlet run (costs tokens)
